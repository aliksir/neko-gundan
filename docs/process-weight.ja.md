# プロセスウェイト — ライトからストリクトまで

全てのタスクに同じ儀式は不要。プロセスウェイトで、タスクに合ったプロセスを選べる。

## 早見表

| ウェイト | トリガーキーワード | 何が起きるか |
|---------|-----------------|-------------|
| **ライト** | 「ライトで」「サクッと」「軽くやって」「quick fix」 | 簡易ゲート、セルフチェック可、計画書/報告書なし |
| **標準** | （デフォルト） | 全ゲート、独立レビュー、標準プロセス |
| **ストリクト** | 「厳密に」「慎重に」「リリース前」「strict mode」 | 全ゲート+ensemble judge、ISV、仲裁者待機 |

## ライトモード詳細

ライトモードは本当に小さいタスク向け: タイポ修正、設定変更、1-2ファイルの変更。

**簡略化されるもの:**
- 完了ゲート → 簡易ゲート（テスト+diff+コミットのみ）
- レビュー → セルフチェック可（実装者≠レビュアーを強制しない）
- 計画書/報告書 → 1行サマリ
- ISV/ホワイトボード → スキップ

**簡略化されないもの（安全性は絶対に下げない）:**
- ファイル削除 → `_deleted/` への退避は必須
- 競合防止 → 有効のまま
- 安全Tier → Tier 1は絶対禁止のまま
- FIDES信頼レベル → 外部データのLOWタグ付けは必須

## エージェント格上げ（ESCALATION-001）

核心的な仕組み: エージェントがリスクを発見したら、**ライトモードに異議を申し立てる**ことができる。

### 格上げトリガー

| トリガー | 例 |
|---------|---|
| 変更ファイル3つ以上 | 「1ファイルのはずが3ファイルに影響します」 |
| DB/API変更あり | 「マイグレーションが必要です」 |
| セキュリティ関連 | 「認証ロジックに触ります」 |
| テストが予期せず失敗 | 「既存テストスイートが壊れてます」 |
| 専門的判断 | 「見た目以上に複雑です」 |

### フロー

```
1. エージェントがライトモード作業中にリスクを検出
2. ESCALATION-001を理由付きで申請
3. 親方猫/仕事猫が判断: 承認 / 却下 / 部分格上げ
4. 作業はそのまま続行（やり直し不要）
```

### 重要ルール

- **格上げは罰されない** — 不要な格上げの方が、リスクの見逃しよりはるかにマシ
- **格下げは人間の承認が必要** — エージェントは格上げできるが、格下げできるのは人間だけ
- **作業は続行** — 格上げ＝やり直しではない

## ストリクトモード詳細

ハイステークスな変更に使う:

**標準に加えて追加されるもの:**
- Ensemble judge（3戦略評価）
- ISV記録必須
- 仲裁者待機
- 成功時もReflexion（成功からも学ぶ）
- 積極的ポーリング（5分間隔）

## 使用例

### ライト: タイポ修正
```
人間: 「README.mdのタイポ直して、ライトで」
→ エージェントが修正、簡易ゲート（テスト+diff+コミット）、完了
```

### 標準: 機能追加（デフォルト）
```
人間: 「ダークモードを追加して」
→ フルプロセス: 計画 → 実装 → レビュー → 完了ゲート
```

### ライト → 標準への格上げ
```
人間: 「設定ファイルを更新して、ライトで」
エージェント: 「ESCALATION-001: この設定変更は依存する4ファイルとDBマイグレーション
              が必要です。標準への格上げを要請します。」
親方猫: 「承認。標準に切り替え。」
→ 現在の進捗からフルプロセスで続行
```

### ストリクト: リリース前
```
人間: 「デプロイ前の最終チェック、厳密に」
→ Ensemble judge、ISV記録、全ゲート証跡付き、仲裁者待機
```

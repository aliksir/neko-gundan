# 計画書テンプレート（implement フェーズ用）

> このテンプレートは `/neko-gundan implement` の入力として使う計画書のガイドです。
> フォーマットの完全一致は不要。LLMが読めれば十分です。
> 人間が書いても、他AIが書いても、猫軍団の design フェーズが出力したものでもOK。

## 必須項目（これがないと実装を始められない）

### 1. 何を作るか（スコープ）
どんな機能・変更を実装するのか。1-3文で。

### 2. 成功基準
実装が「完了した」と判断できる条件。テスト可能な形式が理想。
- 例: 「ログイン画面が表示される」「APIが200を返す」「テストが全件通る」

### 3. 対象プロジェクト
プロジェクト名とディレクトリパス。

## あると助かる項目（なくても動けるが、あると精度が上がる）

### 技術スタック
言語・フレームワーク・DB等。既存プロジェクトなら省略可（コードから読み取れる）。

### 作業手順
実装の順序。ステップ形式。

### DB設計
テーブル定義・ER図。DB変更がある場合。

### API設計
エンドポイント一覧・リクエスト/レスポンス形式。

### UI設計
画面一覧・ワイヤーフレーム・デザインURL。

### 制約・注意事項
「既存のXXX機能を壊さないこと」「YYYライブラリは使わないこと」等。

### やらないこと（スコープ外）
明示的に除外する範囲。

### 合格基準（Sprint Contract）

計画書の「成功基準」を**検証可能なチェックリスト**に落とし込んだもの。
Evaluator（レビュアー）はこの契約に照らしてのみ合否を判定する。

**書き方ルール:**
- `- [ ]` のチェックリスト形式で記述する
- 各項目は **PASS/FIX の二値判定が可能** な文言にする
- **禁止ワード**: 「良い」「適切な」「十分な」「きれいな」「正しい」「わかりやすい」等の曖昧語は使用禁止
- 判定カテゴリ（例: 機能、品質、事実）ごとにグループ化すると判定しやすい

**スコープバインドルール:**
- レビュアーは合格基準にない観点で不合格にしない（スコープクリープ防止）
- 合格基準外で発見した問題は、OBJECTION として別途報告する

```markdown
## 合格基準（Sprint Contract）

### 機能（実装判定）
- [ ] POST /api/auth/login が有効な認証情報でJWTトークンを返す
- [ ] 不正なパスワードで401ステータスを返す

### 品質（review判定）
- [ ] パスワードが平文で保存されていない（bcryptまたはargon2を使用）
- [ ] JWTの有効期限が15分以内に設定されている

### 事実（fact-check判定）
- [ ] READMEの認証フロー図が実装と一致する
```

---

## 記入例（最低限）

```markdown
# ユーザー認証機能

## スコープ
メールアドレス+パスワードによるログイン・ログアウト機能を追加する。

## 成功基準
- POST /api/auth/login でJWTトークンが返る
- POST /api/auth/logout でセッションが無効化される
- 不正なパスワードで401が返る

## 対象
my-app
```

# 猫軍団 ワークフロー定義

> 既存の `~/.claude/workflows/*.md` は汎用フロー。このファイルは**猫軍団固有の拡張**のみを定義する。

---

## フェーズ一覧

```
PLAN → DESIGN → SETUP → EXECUTE → REVIEW → VERIFY → REPORT
```

### PLAN（計画フェーズ）

| 項目 | 内容 |
|------|------|
| 担当 | 親方猫 (oyakata-neko) |
| 開始条件 | 総司令からのタスク受領 + Start Gate通過 |
| 終了条件 | Milestone / Wave / Task に分解完了、成功基準定義済み、**全成果物が存在** |
| 成果物 | `plans/{プロジェクト名}_*.md`（計画書）、`checklist/{日付}_{プロジェクト名}.md`（QA/作業チェックリスト）、`status/dashboard.md`（中隊以上）、TaskCreate 完了 |
| 計画ゲート | スコープ外の明示 + 定量的な成功基準（CLAUDE.md参照） |
| 完了確認 | `ls` で計画書・チェックリスト（・ダッシュボード）の存在を確認。**全て揃って初めてPLANフェーズ完了** |

### DESIGN（設計フェーズ）

| 項目 | 内容 |
|------|------|
| 担当 | 仕事猫 (shigoto-neko) / 現場猫 (genba-neko) |
| 開始条件 | PLANフェーズ完了 |
| 終了条件 | 全設計ゲート通過 + 各レビュー承認済み |
| 成果物 | `plans/{プロジェクト名}_db_design.md`、API/UI設計書 |

#### サブフェーズ

```
DB設計 → DBレビュー → API設計 + UI設計（並行）→ 各レビュー
```

- **DB不使用プロジェクト**: DB設計を `[N/A]` と記録してスキップ
- **API/UIが不要な場合**: 同様に `[N/A]`
- **小規模変更（カラム1つ追加等）でもDB設計→レビューを通す**

#### DB設計ゲート

| チェック項目 | 確認観点 |
|------------|---------|
| ER図/スキーマ定義 | テーブル構造・リレーションが文書化されている |
| 正規化 | 第3正規形以上。非正規化する場合は理由を明記 |
| インデックス設計 | 主要クエリパターンに対応したインデックスが定義されている |
| 命名規約 | snake_case、既存テーブル・カラムとの一貫性 |
| 拡張性 | 将来の変更（カラム追加・テーブル分割等）への影響分析 |
| マイグレーション | 既存データへの影響、ロールバック手順 |

#### DBレビュー観点

| 観点 | 確認内容 |
|------|---------|
| 正規化 | 第3正規形以上か。非正規化がある場合、パフォーマンス理由が明記されているか |
| インデックス | WHERE/JOIN/ORDER BYで使われるカラムにインデックスが定義されているか |
| 拡張性 | 将来のカラム追加・テーブル分割を想定した設計か |
| 命名規約 | snake_case統一。既存テーブル・カラムとの命名一貫性 |
| データ型 | 適切な型選択。NULL許容の妥当性 |
| 制約 | PRIMARY KEY、FOREIGN KEY、UNIQUE、NOT NULL、DEFAULT値が適切か |
| マイグレーション | 既存データへの破壊的変更がないか。ロールバック可能か |

#### API/UI設計ゲート

| チェック項目 | 確認観点 |
|------------|---------|
| エンドポイント/画面一覧 | 必要なAPI・画面が洗い出されている |
| DB設計との整合性 | DBスキーマとAPI/UIのデータフローが一致 |
| レビュー通過 | 設計者≠レビュアーで確認済み |

### SETUP（準備フェーズ）

| 項目 | 内容 |
|------|------|
| 担当 | 仕事猫 (shigoto-neko) |
| 開始条件 | PLANフェーズ完了 |
| 終了条件 | 各現場猫へのタスク割り当て完了、依存関係整理済み |
| 成果物 | TaskUpdate (owner + blockedBy 設定)、ホワイトボード初期化 |
| Concurrencyチェック | spawn前に `config/concurrency.json` を参照（必須） |

### EXECUTE（実行フェーズ）

| 項目 | 内容 |
|------|------|
| 担当 | 現場猫 (genba-neko) / 玄人猫 (kurouto-neko) |
| 開始条件 | blockedBy タスクがすべて completed |
| 終了条件 | 担当タスクの実装完了 + 自己確認（完了ゲート通過） |
| 成果物 | 実装ファイル、TaskUpdate (completed)、仕事猫への報告 |
| Stall対策 | `scripts/stall-detector.sh` が300秒無更新を検知（後述） |

### REVIEW（レビューフェーズ）

| 項目 | 内容 |
|------|------|
| 担当 | 仕事猫（実装者とは別） |
| 開始条件 | EXECUTEフェーズの成果物受領 |
| 終了条件 | 承認 または 差し戻し（指摘リスト作成） |
| 成果物 | レビューレポートファイル（Context Rot対策でファイル経由） |
| 制約 | **edit: false**（コード改変禁止、指摘のみ） |

### VERIFY（検証フェーズ）

| 項目 | 内容 |
|------|------|
| 担当 | QA猫（Opusモデル、実装者とは別） |
| 開始条件 | REVIEWフェーズ承認後 |
| 終了条件 | 完了ゲート全項目通過 + **Proof of Work検証PASS** |
| 成果物 | QAレポート、テスト結果、**PoW結果JSON** |
| 完了ゲート | Read確認 + Grep確認 + 動作テスト + 報告の誠実性（CLAUDE.md参照） |

#### Proof of Work（機械的検証ゲート）

タスク完了の「主張」ではなく「証拠」で判定する。VERIFYフェーズで必ず実行：

```bash
bash scripts/proof-of-work.sh <project_dir> --task-id <task_id> --review-complete
```

検証ゲート:
- **test_pass**: テストスイート全通過
- **build_success**: ビルドコマンド exit 0
- **review_complete**: 実装者以外のレビュー完了
- **no_regressions**: 既存テストが壊れていない

結果: `status/proof-of-work/{task_id}-{date}.json`

- 全ゲートPASS → `PROOF_VERIFIED` → 完了宣言OK
- 1つでもFAIL → `PROOF_FAILED` → 完了宣言禁止

### REPORT（報告フェーズ）

| 項目 | 内容 |
|------|------|
| 担当 | 仕事猫 → 親方猫 |
| 開始条件 | VERIFYフェーズ完了 |
| 終了条件 | 総司令への最終報告完了 |
| 成果物 | `C:\work\result\YYYYMMDD_{プロジェクト名}.md`、送信メッセージ |

## Stall Policy（停止検出ポリシー）

### 判定基準
- `in_progress` 状態のタスクが **300秒（5分）** 更新なし → **stall（停止）判定**
- 検出スクリプト: `scripts/stall-detector.sh`（30秒間隔でポーリング）

### 対応フロー
```
stall検出
  → [1] 仕事猫 ping（SendMessage で確認）
  → [2] 応答なし（30秒待機）→ shutdown_request 送信
  → [3] 応答なし → respawn（新しいエージェントで再担当）
  → [4] 5回失敗 → 親方猫へエスカレーション
```

### アラートファイル
アラートは `status/alerts/` 以下に出力:
```json
{
  "type": "stall",
  "task_id": "タスクID",
  "agent": "エージェント名",
  "stalled_since": "ISO8601タイムスタンプ",
  "detected_at": "ISO8601タイムスタンプ"
}
```

## Concurrency Policy（並列数制限ポリシー）

設定ファイル: `config/concurrency.json`

### spawn前の必須チェック
1. 全エージェント合計が `max_concurrent_agents`（5）を超えないか
2. 役割別上限を超えないか（oyakata:1, shigoto:2, genba:4, kurouto:2）
3. `in_progress` 状態のタスクが4件以内か

**spawn前チェックは必須。超過する場合はキューで待機させること。**

## Quality Gate（品質ゲート）

レビューループプロトコル（takt由来、猫軍団QAに統合済み）:

1. **実装者 ≠ レビュアー**: 書いた猫が自分でレビューしない
2. **レビュアーは読み取り専用**: `edit: false`。コード改変禁止、指摘のみ
3. **ループ上限3回**: 3サイクル超過で仲裁者（Opus）が介入

```
implement → review(edit:false) → [問題あり] → fix → review → ... (最大3回)
                                  [問題なし] → supervise → COMPLETE
```

## Token Budget（トークン予算）

### 計測方式
- **作業時間プロキシ**: 実際のトークン数は取得困難なため、**作戦の経過時間**を代替指標とする
- 計測スクリプト: `scripts/token-tracker.sh`

### 使い方
```bash
# 作戦開始時
bash scripts/token-tracker.sh start "作戦名"

# 作戦終了時
bash scripts/token-tracker.sh stop "作戦名"

# 状態確認
bash scripts/token-tracker.sh status "作戦名"
```

出力先: `status/token-usage/{作戦名}-{日付}.json`

## 既存ワークフローとの関係

| ファイル | 役割 |
|---------|------|
| `~/.claude/workflows/bug-fix.md` | バグ修正の汎用フロー |
| `~/.claude/workflows/new-feature.md` | 機能追加の汎用フロー |
| `~/.claude/workflows/refactor.md` | リファクタリングの汎用フロー |
| `~/.claude/workflows/security-audit.md` | セキュリティ監査の汎用フロー |
| `~/.claude/workflows/research.md` | 調査・研究の汎用フロー |
| **このファイル** | **猫軍団固有の拡張**（Stall検出、Concurrency、QAゲート、Token追跡） |

**原則**: 汎用フローと猫軍団拡張を組み合わせて使う。重複定義は避ける。

## フェーズ別独立実行

通常は PLAN → DESIGN → ... → REPORT を一気通貫で実行するが、**個別フェーズだけを指定実行**できる。

### コマンド

```
/neko-gundan design "製品仕様の説明"
/neko-gundan implement "計画書パス or 仕様説明"
/neko-gundan review "レビュー対象"
/neko-gundan test "テスト対象"
/neko-gundan "タスク説明"           ← 従来通り全フロー
```

### ルーティング

先頭キーワードでフェーズを判定する。キーワードがなければ全フロー。

| 先頭キーワード | フェーズ | 実行内容 |
|--------------|---------|---------|
| `design` | 設計 | 計画・DB設計・API/UI設計を実施。実装はしない |
| `implement` | 実装 | 指定された計画書を読んで実装のみ |
| `review` | レビュー | 計画書/コードのレビューのみ。修正はしない |
| `test` | テスト | テスト作成・実行・品質確認 |
| （なし） | 全フロー | PLAN → DESIGN → SETUP → EXECUTE → REVIEW → VERIFY → REPORT |

### 入力テンプレート

`templates/` に各フェーズ用のテンプレートを用意している。**フォーマットの完全一致は不要**。人間が書いても、他AIが書いても、最低限の必須項目が読み取れればOK。

| テンプレート | 用途 | 必須項目 |
|------------|------|---------|
| `templates/plan-template.md` | implement用の計画書 | スコープ・成功基準・対象PJ |
| `templates/review-request-template.md` | review用の依頼 | レビュー対象・観点 |
| `templates/test-request-template.md` | test用の依頼 | テスト対象・種別 |

### フェーズ別ゲート

各フェーズの性質に合わせた軽量ゲート。全フロー時の開始/完了ゲートとは独立。

#### Design 開始ゲート（3項目）

| チェック項目 | 確認方法 |
|------------|---------|
| 対象プロジェクト特定 | 何のPJか。新規なら `[新規]`。既存なら Purpose をRead |
| 製品仕様の入力確認 | 設計に必要な情報が揃っているか。不足があれば確認 |
| 既存設計の確認 | `ls plans/{PJ名}_*` で既存の計画書・設計書を確認 |

#### Design 完了ゲート（3項目）

| チェック項目 | 確認方法 |
|------------|---------|
| 計画書の存在 | `plans/` にスコープ・成功基準を含む計画書がある |
| 必要な設計の完了 | DB/API/UI設計のうち必要なものが全て完了。不要なものは `[N/A]` |
| 設計レビュー実施 | 設計者≠レビュアーで確認済み |

#### Implement 開始ゲート（3項目）

| チェック項目 | 確認方法 |
|------------|---------|
| 計画書の存在確認 | 指定パスの計画書を読み込み。スコープ・成功基準が読み取れるか |
| 実装可能レベル判定 | 手順が推測可能な程度の情報があるか。不足なら確認 |
| git status確認 | 対象PJでクリーンな状態か |

#### Implement 完了ゲート（4項目）

| チェック項目 | 確認方法 |
|------------|---------|
| 成功基準の充足 | 計画書の成功基準を1つずつ検証 |
| コードのコミット | `git status` でclean or コミット済み |
| 構文チェック通過 | lint/型チェック実行（該当する場合） |
| 実機動作確認 | テスト実行・CLI実行等。テスト対象がない場合→`[N/A]` |

#### Review 開始ゲート（2項目）

| チェック項目 | 確認方法 |
|------------|---------|
| レビュー対象の特定 | 計画書/コード/両方のいずれかが明確 |
| 対象の可読性確認 | `Read` / `git diff` で確認可能 |

#### Review 完了ゲート（2項目）

| チェック項目 | 確認方法 |
|------------|---------|
| レビュー報告書の出力 | verdict（APPROVE/REQUEST_CHANGES）+ findings |
| 判定の根拠 | ファイルパス・行番号・具体的な指摘を含む |

#### Test 開始ゲート（3項目）

| チェック項目 | 確認方法 |
|------------|---------|
| テスト対象の特定 | PJ名・対象範囲・テスト種別が明確 |
| 実装済みコードの存在 | 対象ディレクトリにコードがある |
| テスト計画書の作成・承認 | テストマトリクス（機能×観点）を含むテスト計画書を作成し、承認を得る |

#### Test 完了ゲート（5項目）

| チェック項目 | 確認方法 |
|------------|---------|
| 単体テスト全件実行 | テストマトリクスの正常系・異常系が全て実施済み |
| 結合テスト全件実行 | 結合テストマトリクスのシナリオが全て実施済み |
| テスト実行結果の証跡 | pass/fail件数・カバレッジ等のコマンド出力 |
| 品質チェック結果 | lint/セキュリティスキャン等の結果。未実施→`[N/A]` |
| 不合格項目の一覧化 | fail・警告・脆弱性がある場合は一覧化 |

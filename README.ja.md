# 猫軍団 - Claude Code マルチエージェントオーケストレーション

> **初めての方へ** スキルをインストールしてClaude Codeで `/welcome-neko` を実行すれば、対話形式でセットアップできます！
> ```bash
> # スキルをインストール
> git clone https://github.com/aliksir/neko-gundan.git
> cp -r neko-gundan/skills/welcome-neko ~/.claude/skills/
> # Claude Codeで /welcome-neko を実行
> ```

**[English README](README.md)** | **PROプラン？ → [子猫軍団（ライト版）](README.koneko.ja.md)**

> Claude Codeは1体でもコードを書ける。でも自分のミスを自分で見つけたり、悪い判断を止めたり、複数ファイルを安全に協調して変更することはできない。猫軍団は作業をチームに分割する — コードを書いた猫がレビューすることは絶対にない。

## こんな人・使い方に向いている

**向いている:**
- エージェントにファイルを消された、動いてたコードを壊された、「確認しました」が嘘だった経験がある
- 品質事故がリアルに時間を奪うプロダクト開発をしている（使い捨てプロトタイプではない）
- AI生成コードにセカンドオピニオンが欲しいが、毎行レビューはしたくない
- 複数ファイルの変更を並列で進めたいが、エージェント同士の衝突が怖い

**向いていない:**
- プロトタイプや実験が主で、正確さより速さが優先
- 100体以上の専門エージェントのカタログが欲しい — [VoltAgent](https://github.com/VoltAgent/core) や [wshobson/agents](https://github.com/wshobson/agents) を検討してほしい
- `quality` や `security` 1モードでも重く感じる — 標準のClaude Code subagentsで十分かもしれない

猫軍団は万能ツールではない。こだわっているのは一つだけ: **「終わった」ではなく「正しいと証明された」。**

## おすすめ構成 — 「迷ったらこれ」

| あなたの状況 | おすすめ構成 | 理由 |
|------------|------------|------|
| 個人開発、安全ネットが欲しい | `security` | エージェント不要。誤削除・危険操作を防ぐルールだけ |
| 小規模プロダクト、品質が大事 | `quality+security` | レビュアー1体 + 安全ルール。コスパ最良のスタート地点 |
| 複数ファイル変更、チーム規模 | `all` | フルチーム構造。通常タスクは標準、リリースは厳密に |

まず軽く始めて、後から追加できる。`install.sh` を再実行するだけでモード追加可能。

## クイックスタート

```bash
git clone https://github.com/aliksir/neko-gundan.git

# 必要なモードだけ選んでインストール（quality, implement, plan, security）
bash neko-gundan/scripts/install.sh quality+security ./your-project

# または全部入り
bash neko-gundan/scripts/install.sh all ./your-project
```

インストーラが必要なファイルだけコピーし、CLAUDE.mdに追加するスニペットを表示する。

> **フレームワーク全体は要らない？** `security`（エージェント不要、安全ルールだけ）や `quality`（レビュアーだけ）から始められる。[全モード詳細](docs/modes.ja.md)

### フルインストール（全モード）

```bash
bash neko-gundan/scripts/install.sh all ./your-project
bash neko-gundan/scripts/setup.sh  # ランタイムディレクトリを初期化
```

### アップデート

既にインストール済み？ neko-gundanを最新にして差分を確認:

```bash
cd neko-gundan && git pull
bash scripts/install.sh --update all ./your-project
```

変更があるファイルごとにdiffを表示し、上書きするか手元を維持するか選べる。カスタマイズしていないファイルはそのまま更新される。

**ファイル種別ごとの推奨マージ戦略:**

| ファイル種別 | 戦略 | 理由 |
|------------|------|------|
| `rules/*.md` | upstream優先 | プロトコル改善を取り込む。カスタマイズはconfigで行う |
| `agents/*.md` | upstream優先 | エージェント動作の更新。PJ固有の調整はCLAUDE.mdで |
| `modules/*.md` | upstream優先 | モジュール定義はフレームワーク管理 |
| `neko-gundan.config.yaml` | **ローカル優先** | あなたのPJのモジュールON/OFF設定 |
| `CLAUDE.md` スニペット | **手動確認** | 新機能とPJ固有の指示をマージ |
| `scripts/*.sh` | upstream優先 | バグ修正と新機能 |

## アップデート確認

インストーラは `~/.claude/.neko-gundan-manifest.json` にインストール済みのモードとファイル一覧を記録する。アップデート確認スクリプトはこれを使って新バージョンを通知する。

**手動チェック:**

```bash
bash neko-gundan/scripts/check-update.sh
# キャッシュを無視して即時チェック:
bash neko-gundan/scripts/check-update.sh --force
```

新バージョンがある場合:

```
🔔 猫軍団: 新バージョン v1.8.0 が利用可能です（現在: v1.7.0）
   インストール済みモード: quality+implement
   → bash neko-gundan/scripts/install.sh --update quality+implement ./your-project
```

**セッション開始時の自動チェック（オプトイン）:**

Claude Codeの設定ファイル（`~/.claude/settings.json`）に追加:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "type": "command",
        "command": "bash ~/.claude/neko-gundan/scripts/check-update.sh &",
        "timeout": 10000
      }
    ]
  }
}
```

バックグラウンドで実行され、更新がある場合のみ通知する。自動更新はしない。

**注意事項:**
- チェック結果は24時間キャッシュ（`~/.claude/.neko-gundan-update-cache`）
- curlが使えない環境はサイレント終了（エラーにならない）
- マニフェスト（`~/.claude/.neko-gundan-manifest.json`）はインストーラが自動生成する

### Gate Guard Hook（オプトイン）

開始ゲートの構造的コンプライアンスを機械的に強制する。`plans/` または `checklist/` にファイルがない状態でプロジェクトのソースコードを `Edit`/`Write` しようとするとブロックする — 計画フェーズのスキップを物理的に防止。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit",
        "hooks": [{ "type": "command", "command": "node path/to/hooks/gate-guard.mjs", "timeout": 3 }]
      },
      {
        "matcher": "Write",
        "hooks": [{ "type": "command", "command": "node path/to/hooks/gate-guard.mjs", "timeout": 3 }]
      }
    ]
  }
}
```

`plans/` と `checklist/` ディレクトリ内にプロジェクト名を含むファイルがあるかチェックする。メタディレクトリやメタファイル（CLAUDE.md、handover.md等）はスキップされるので、ゲート成果物自体の作成は妨げない。

## あなたがやることは3つだけ

プロトコルもモジュールも安全ルールも、全部自動で動く。あなたがやるのは3つだけ:

1. **インストール** — モードを選んでインストーラを実行。30秒で終わる。
2. **タスクを伝える** — 普通の言葉でやりたいことを言う。「ライトで」「厳密に」で丁寧さを調整。
3. **証拠を確認する** — エージェントは「終わりました」ではなく証拠（テスト結果、diff）を出す。あなたはコードではなく証拠を確認する。

役割の割り当て、レビュー分離、異議申立、安全チェック — 全部裏で勝手に回る。

## 仕組み

```
総司令（人間）
    |
親方猫（親方 / Opus）--- 戦略立案・委譲
    |
仕事猫（中間管理職 / Sonnet）--- タスク分解・品質確認
    |
現場猫（実働部隊 / Sonnet）--- 実装
    |
玄人猫（専門家 / Opus）--- 独立レビュー
```

タスクの規模に応じて自動的にチーム編成を調整:

| 規模 | 判定基準 | 編成 |
|------|---------|------|
| 偵察 | 質問・調査 | 親方猫が直接対応 |
| 小隊 | 1-2ファイル、または3-5ファイルの単純リファクタ | 仕事猫が単独対応 |
| 中隊 | 3-5ファイル AND 設計判断を含む | 仕事猫 + 現場猫1-2体 |
| 大隊 | 6ファイル以上 | 仕事猫 + 現場猫3体 |

## 主要機能

### 設計フェーズの必須化

全タスクは**計画 → 設計 → 実装 → 品質確認**のフローに従う。設計書（`designs/`）は必須成果物。

- **コード変更あり**: 設計方針・判断理由を記録（なぜこのアプローチか、代替案は何か）
- **コード変更なし**（ドキュメント・設定等）: 「設計対象なし」と理由を記載（ファイルは必須）
- `commit-guard` hookが `designs/` 不在時にコミットをブロック

「何を変えたか」だけでなく「なぜそう作ったか」を常に遡れるようにする。

### フェーズ別独立実行

全フロー一気通貫ではなく、個別フェーズだけを実行できる。人間や他AIが一部のフェーズを担当する場合に便利。

```bash
/neko-gundan design "認証機能を追加"          # 設計のみ — 実装しない
/neko-gundan implement "plans/auth.md"        # 計画書（人間/AI作成）から実装のみ
/neko-gundan review "feature/auth ブランチ"    # レビューのみ — 修正しない
/neko-gundan test "src/auth/"                 # テスト・品質確認のみ
/neko-gundan "認証機能を追加"                  # 全フロー（デフォルト）
```

各フェーズに専用の軽量ゲートあり。入力テンプレートは `templates/` にあるが、フォーマットの完全一致は不要（スコープ・成功基準が読み取れればOK）。詳細は [WORKFLOW.md](docs/WORKFLOW.md#フェーズ別独立実行) を参照。

#### フェーズ別必要ファイル

| フェーズ | 必要な入力 | 出力 | 不在時の自動作成 |
|---------|-----------|------|-----------------|
| `design` | Purposeファイル（あれば） | `plans/`, `designs/` | designs/ テンプレート |
| `implement` | `designs/*.md`（推奨）、不在時は `plans/*.md`（必須） | ソースコード、コミット | designs/（「設計対象なし」で自動作成） |
| `review` | 計画書 / 設計書 / コード（対象種別で照合元が異なる） | レビュー報告書 | — |
| `test` | ソースコード、テスト計画書（マトリクス） | テスト結果 | — |
| （全フロー） | — | 上記すべて | — |

> **ファイルが見つからない場合**: 各フェーズは開始ゲートで必要ファイルをチェックします。不足していれば「XXXファイルが必要です」と具体的に表示されます。

**テストフェーズ**はテスト計画書（マトリクス）による網羅性管理を含む：

```
1. 対象コードを読む → 機能一覧を洗い出す
2. テスト計画書を作成（機能×観点のマトリクス）
3. 総司令に提示 → 承認
4. 単体テスト（正常系・異常系は必須）
5. 結合テスト（機能間連携シナリオは必須）
6. 結果をマトリクスに記録 → 報告
```

| テスト観点 | 必須 | 説明 |
|-----------|------|------|
| 正常系 | **必須** | 期待通りの入力→期待通りの出力 |
| 異常系 | **必須** | 不正入力・null・型違い・未認証 |
| 境界値 | 推奨 | 0/1/MAX/空文字/上限値±1 |
| 状態遷移 | 該当時 | 状態変化のある機能の前後確認 |

### 異議を申し立てるエージェント

エージェントは命令に従うだけではない。不適切な指示に**異議を申し立てる義務**がある。

- **OBJECTION-001**（現場猫 → 仕事猫）：「この指示は既存機能を壊します」
- **OBJECTION-002**（仕事猫 → 親方猫）：「この戦略は目的と矛盾しています」

各異議には**事実 + 懸念 + 代替案**が必要。

### 証跡ベースの品質ゲート

全てのタスクは証跡付きのゲートを通過する必要がある。「確認した」は許されない — 「これが証拠だ」だけが有効。

```
| # | チェック項目      | 状態 | 証跡                                  |
|---|------------------|------|---------------------------------------|
| 1 | テスト通過        | PASS | `npm test`: 42 passed, 0 failed       |
| 2 | 意図しない差分なし | PASS | `git diff` は対象ファイルのみ          |
| 3 | 異議解決済み       | PASS | ホワイトボードに未解決異議なし         |
```

### チェックリスト外出し — 見える化

完了ゲートのチェックリストをmarkdownファイルとして外部出力できる。セッション終了後でも品質判断の経緯を振り返れる。

```
_checklist/
  20260310_my-project.md   ← ゲート結果と証跡
```

`checklist_export` を有効にし（`recommended`・`full` プリセットではデフォルトON）、CLAUDE.mdで出力先を設定:

```yaml
checklist_output_dir: "./_checklist/"
```

### 品質メトリクス — ゲートは機能しているか？

AI生成コードの量は人間のレビュー帯域より速く増える。品質トレンドが見えなければ、ゲートは形骸化する。このモジュールは品質プロセスが実際に機能しているかを追跡する。

```markdown
| 指標 | 値 | 傾向 | 意味 |
|------|-----|------|------|
| ゲート通過率 | 87% | → | 完了ゲートのPASS率。低い＝品質に穴 |
| スキップ率 | 23% | ↑ ⚠️ | N/Aスキップ率。高い＝ゲート形骸化の兆候 |
| 平均レビュー周回数 | 1.3 | ↓ | 1発OKばかり＝レビューが甘い可能性 |
```

完了ゲート実行時にエージェントがメトリクスを計算し、閾値を超えていればアラートを記載する。スキップ率上昇、全レビュー1発通過、人間介入ゼロ継続などが検知対象。

**基準値の目安**（出発点 — プロジェクトに応じて調整）:

| 指標 | 健全 | 要注意 | 要対処 |
|------|------|-------|--------|
| ゲート通過率 | 70-95% | 50-70% or 95%超 | 50%未満 |
| スキップ率 | 20%未満 | 20-35% | 35%超 |
| 平均レビュー周回数 | 1.2-2.0 | 1.0（全件1発通過）or 2.5超 | 3.0超 or 1.0が5件以上継続 |
| 人間介入 | 0.2-1.0/タスク | 10件以上ゼロ | ゼロ継続（監視なし？） |

*レビュー周回数が1.0のまま続くのは怪しい — レビューが形式だけになっている可能性。適度なpushbackは健全な証拠。*

`quality_metrics` を有効にし（`full` プリセットではデフォルトON）、CLAUDE.mdで出力先を設定:

```yaml
metrics_output_dir: "./_metrics/"
```

### 生ログ — 全行動の監査証跡

「何を見てヨシッって言ったんですか？」生ログはエージェントの**全行動**を記録する — 読んだファイル、変更のdiff全文、実行したコマンドとその出力、判断の理由。

```markdown
### [09:41:03] Edit src/checks/inbound.js:31
```diff
+ /\b(?:Invoke-Expression|IEX)\s*[\s(]/i,
+ /\bStart-Process\b/i,
```

### [09:41:05] Bash node -e "const {CHECKS}..."
```
IN-002 patterns: 16
```
exit: 0
```

ログは**作業完了後**にまとめて生成（実行中のオーバーヘッドなし）。`git diff` とエージェント報告のクロスチェックで正確性を担保。

`raw_log` を有効にして使用（`full` プリセットではデフォルトON）:

```yaml
shitsuke:
  raw_log: true
```

### 監査証跡 — 開発監査エビデンス

「誰がいつ何を承認したか、証明できますか？」監査証跡モジュールは、会話コンテキストを超えて永続化する4種の構造化エビデンスを記録する:

| 記録 | 内容 | ファイル |
|------|------|---------|
| **トレーサビリティマトリクス** | 要件 → 設計 → コミット → テスト | `audit/{project}_traceability.md` |
| **承認ログ** | 誰が・いつ・何を・なぜ承認したか | `audit/{project}_approvals.md` |
| **変更管理台帳** | スコープ変更の理由と影響 | `audit/{project}_changes.md` |
| **監査サマリー** | 全エビデンスの集約ビュー | `audit/{project}_audit-report.md` |

トレーサビリティはタスク分解時に発番されるREQ-IDで追跡。各要件を定義→実装→テスト検証まで追う:

```markdown
| ID | Requirement | Commit | Test | Status |
|----|-------------|--------|------|--------|
| REQ-001 | ユーザー認証 | abc1234 | test_auth.py:TestLogin | VERIFIED |
| REQ-002 | データ出力 | — | — | PENDING |
```

後からログが必要になった場合も、rebuild機能でgit履歴・報告書・生ログから再構築できる:

```
承認ログ再構築:      result/ + raw-log + git履歴 → approvals_rebuilt.md
トレーサビリティ再構築: plans/ + git log + テスト → traceability_rebuilt.md
ファイル追跡:        git log --follow + _deleted/ → 移動・削除履歴
```

設定で `audit_trail` を有効化（`full` プリセットでON）:

```yaml
shitsuke:
  audit_trail: true
```

### 実装者 != レビュアー

自己承認を防ぐ3原則:

1. コードを書いた猫が自分でレビューすることは**絶対にない**
2. レビュアーは**読み取り専用** — 指摘のみ、コード変更禁止
3. 3サイクル超過で仲裁者（Opus）が最終判断

### 安全対策

- **ファイル削除安全策**: 即削除せず `_deleted/` に退避
- **競合防止**: 2体以上のエージェントが同一ファイルを同時編集することを禁止
- **信頼レベル（FIDES）**: 外部データは明示的にLOW信頼としてタグ付け
- **破壊操作Tier**: Tier 1は絶対禁止、Tier 2は要確認

### 必要なものだけ入れる（モード）

課題に合うパーツだけインストール:

| モード | 何を解決するか | エージェント必要？ | プラン |
|--------|--------------|------------------|--------|
| **koneko** | 低予算で品質を確保 | 1体（軽量レビュアー） | PRO |
| **quality** | 自己レビュー、未検証の「完了」 | 1体（レビュアー） | MAX 5+ |
| **implement** | 大規模な複数ファイル変更 | 2体（マネージャー + ワーカー） | MAX 5+ |
| **plan** | 複雑なタスク分解 | 1体（親方猫） | MAX 5+ |
| **security** | 誤削除、危険な操作 | 不要（ルールのみ） | 全プラン |

自由に組み合わせ可: `quality+security`、`plan+implement`、`all`。[全モード詳細](docs/modes.ja.md)

| いつ決めるか | 仕組み | 何を制御するか | 例 |
|-------------|--------|---------------|---|
| **導入時に** | [モード](docs/modes.ja.md) | `.claude/` に何を入れるか | `quality+security` |

<summary>プロセスウェイト — ライトからストリクトまで</summary>

全てのタスクにフルプロセスは不要。「ライトで」と言えばサクッと、「厳密に」と言えば最大検証:

```
「このタイポ直して、ライトで」  →  簡易ゲートのみ（テスト+diff+コミット）
「認証機能を追加して」          →  標準（全ゲート、レビュー、異議申立）
「デプロイ準備、厳密に」        →  最大検証（ensemble、ISV、仲裁者待機）
```

エージェントが「ライト」のタスクに危険を感じたら**格上げを申請**できる:
```
ESCALATION-001: プロセスウェイト格上げ要請
現在: ライト → 提案: 標準
理由: 「DBマイグレーション含む4ファイルに変更が必要」
```

安全プロトコル（競合防止、削除安全策）は**絶対に軽減されない** — ライトモードはプロセスを軽くするが、安全性は下げない。

#### ライトで十分な典型例

タイポ修正、コメント編集、ログ文言変更、CSS微修正、テスト名変更、設定値の単純更新、依存バージョンバンプ、README編集、import整理、デッドコード削除。

#### 標準以上が必要な典型例

DBマイグレーション、新APIエンドポイント、認証変更、ファイル削除ロジック、複数サービス連携、デプロイ設定、権限・アクセス制御、データモデル変更。

迷ったらライトで始める — エージェントがリスクを検知したら格上げを申請する（ESCALATION-001）。

</details>

<details>
<summary>比較: 標準Subagents / LangGraph・CrewAI との違い</summary>

#### 標準Subagentsとの違い

Claude Code標準のSubagentsは強力。猫軍団はその上に**運用ガードレール**を載せる:

| | 標準Subagents | 猫軍団 |
|---|---|---|
| 自己レビュー | 自分で書いたコードを自分でレビュー可能 | **実装者≠レビュアーを強制** |
| 品質の証明 | 「確認した」で通る | **証跡が必要**（テスト結果、git diff） |
| 不適切な指示 | そのまま実行される | **異議申立義務**（OBJECTIONプロトコル） |
| ファイル削除 | 即削除、復元不可 | **`_deleted/` に退避** |
| 並列編集 | 調整なし | **競合防止** |
| 品質トレンド | 壊れるまで見えない | **メトリクスが追跡**（ゲート通過率、スキップ率、レビュー周回数） |

標準Subagentsで十分ならそれでいい。猫軍団は「完了した」ではなく**「正しいと証明された」**が必要な時のためにある。

#### LangGraph / CrewAI との違い

それらはコードベースのオーケストレーションフレームワーク — Pythonでエージェントワークフローを定義する。猫軍団は別のアプローチ: **コードではなくルール**。

| | コードベースFW | 猫軍団 |
|---|---|---|
| 仕組み | Pythonでエージェントグラフを定義 | プロンプトルールでエージェントの振る舞いを定義 |
| 統合 | アプリとは別のシステム | Claude Codeの設定内（`.claude/`）に同居 |
| 導入 | パッケージ導入、オーケストレーションコード記述 | ファイルコピー、CLAUDE.mdにスニペット追加 |
| 部分導入 | 基本的に全部入り | 1モードだけ入れて後から追加OK |
| カスタマイズ | Pythonコードを修正 | Markdownファイルを編集 |

猫軍団はClaude Codeに「憲法」を注入する — エージェントが従う運用ルール。新しいランタイムも依存パッケージも不要。既存のClaude Code環境がそのままチーム構造を獲得する。

#### 猫軍団が負ける点

正直なトレードオフ:

| 観点 | 猫軍団が負ける相手 | 理由 |
|------|------------------|------|
| **役割の豊富さ** | VoltAgent, wshobson/agents | 猫軍団は4役割。あちらは100以上。「データアナリスト」「DevOps」等の専門エージェントが必要ならそちらを |
| **フローの自由度** | LangGraph, CrewAI | 猫軍団は固定階層（親方→管理職→実働→レビュー）。任意のDAGワークフローが必要ならコードベースFWの勝ち |
| **軽さ・速さ** | 標準Claude Code subagents | どんなフレームワークもオーバーヘッドがある。単発の軽いタスクならraw subagentsのほうが速くて安い |
| **言語/ランタイム対応** | コードベースFW | 猫軍団はClaude Code専用。あちらは複数LLMプロバイダ・ランタイムに対応 |

猫軍団が最適化しているのは1点だけ: **作業が正しいことの証明**。それがボトルネックでないなら、シンプルなツールのほうが良い。

</details>

## 設計思想

このフレームワークは理論から設計されたものではない。AIエージェントが本番ファイルを削除し、誤った判断を下し、動作中の機能を壊した実際のインシデントから進化した。全てのプロトコルは、それがなかったために問題が発生した経験に基づいている。

| インシデント | 対策 |
|------------|------|
| エージェントが自分のミスに気づけなかった | 独立レビュアーの必須化 |
| 不適切な指示がそのまま実行された | 双方向異議申立プロトコル |
| 「確認した」に証拠がなかった | 証跡ベースの完了ゲート |
| ファイルを誤って即削除した | `_deleted/` 安全バッファ |
| タスク途中でコンテキストを喪失した | ホワイトボード知識共有 |

## ケーススタディ

猫軍団を使ったプロジェクトの実例（詳細は匿名化）。

<details>
<summary>事例A: 認証機能追加 — 中隊規模のタスクがどう回るか</summary>

**タスク:** Webダッシュボードにユーザー認証を追加（新APIエンドポイント + UI + DB変更）。

**経過:**
1. 親方猫が判定: 5ファイル、DBマイグレーション、新API — 中隊規模（標準ウェイト）
2. DB設計ゲートが `users.email` のインデックス不足をコード前に検出
3. 仕事猫が分担: 現場猫A（API + DB）、現場猫B（UIコンポーネント）
4. 競合防止: APIルートはAに、ReactコンポーネントはBに — ファイル重複なし
5. 玄人猫レビューでセッショントークンのlocalStorage保存（セキュリティリスク）を指摘 → 修正に差し戻し
6. 2回目レビュー: PASS。合計: レビュー2周回、人間介入0回

**フレームワークなしの場合:** localStorageの問題はそのまま出荷された可能性が高い。1体のエージェントが自分で書いた認証実装を自分でレビューすると、書いた時と同じセキュリティ前提を見落としがち。

</details>

<details>
<summary>事例B: 「ただの設定変更」が実はそうじゃなかった — プロセスウェイト格上げ</summary>

**タスク:** 「DB接続設定を更新して、ライトで」

**経過:**
1. ライトウェイトで開始（設定値の更新 — 単純なはず）
2. 現場猫がDBマイグレーション（スキーマバージョン変更）が必要なことを発見
3. ESCALATION-001を提出: ライト → 標準、理由:「DBマイグレーションが3テーブルに影響」
4. 仕事猫が承認。フルゲート発動 — ロールバック検証付きでマイグレーションをテスト
5. 完了ゲートで問題発覚: 正方向のマイグレーションは成功するが、ロールバック時にデータ入りカラムがDROPされる

**フレームワークなしの場合:** 「設定変更」→ サッと編集 → デプロイ → マイグレーション失敗 → 手動ロールバック → データ消失の恐れ。格上げプロトコルが潜在的なインシデントをクリーンな検証済み変更に変えた。

</details>

<details>
<summary>事例C: ゲートがサイレントな破壊を阻止</summary>

**タスク:** ユーティリティ関数のリファクタリング（4ファイル、標準ウェイト）。

**経過:**
1. 現場猫がリファクタリング完了。対象ファイルは全て更新済み、コードは綺麗
2. 完了ゲート項目#2: `git diff` チェック — 関係ないテストファイルに意図しない変更を発見（エディタの自動import書き換え）
3. ゲート状態: FAIL。現場猫が意図しない変更をリバート
4. 再ゲート: PASS。関係ないテストファイルが変更されていないことを確認

**フレームワークなしの場合:** 余計なdiffがサイレントにコミットされていた。無害だったかもしれないし、他の人が依存しているテストを壊していたかもしれない。ゲートは30秒で検出した — 後からデバッグすれば何倍も時間がかかる。

</details>

## トレードオフ

**最終判断は人間。** 猫軍団はAI同士のレビューを追加するが、人間の判断を置き換えるものではない。レビュアーと実装者は同じモデルファミリーなので、同じ盲点を共有し得る。証跡ゲート（`npm test`、`git diff`）は機械的なミスを拾うが、設計判断やビジネスロジックの最終確認は人間の仕事。「より良い初稿」であって「レビュー不要」ではない。

**エージェントが増えればトークンも増える。** 中隊規模（3エージェント）でソロの約2〜3倍。[プロセスウェイト](docs/process-weight.ja.md)でコストを制御できる — 軽い修正なら「ライトで」と言えばフル工程をスキップ。

**増えるもの vs 減るもの:**

| 増えるコスト | 減るコスト |
|---|---|
| トークン消費（中隊規模で2〜3倍） | エージェントが仕込んだバグのデバッグ |
| 初回レスポンス時間 | 誤ファイル削除からの復旧 |
| `.claude/` のプロンプト複雑さ | 「完了」を自称する未検証作業の再レビュー |
| モード/ウェイト体系の学習 | 悪い変更が入った後の原因調査 |

安全ルール（`security` モード）はほぼコストゼロ — プロンプトルールだけで追加エージェント呼び出しなし。トークンコストなしで安全ネットだけ欲しいならここから始める。

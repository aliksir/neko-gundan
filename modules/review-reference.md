## セッション分離レビューの実証根拠（論文根拠: arxiv:2603.12123）

同一セッションで2回レビューしてもF1は24.6%→変化なし。新規セッションに分離するとF1が28.6%に向上（+16%相対改善）。
改善の原因は**コンテキスト汚染の排除**。追加インフラ不要・コスト1セッション分のみ。

- 猫軍団の「実装者≠レビュアー」「TDD分離原則」は本論文の知見と完全一致
- review-protocol.mdの「Context Rot対策」が科学的に支持された
- **同一セッション内での再レビューは効果なし**。必ず別エージェント（別セッション）でレビューすること

## TDD分離原則

同一コンテキストでテスト作成と実装を行うと、テスト作成者の分析が実装者に漏れる（Context Pollution）。
中隊以上では**テスト作成と実装を別エージェントで分離**する：
```
現場猫A: テスト作成 → handoff(action:auto) → 現場猫B: 実装 → 玄人猫: レビュー
```

## 外部ツール結果のJudge統合

玄人猫のルブリック判定前に、以下の外部ツール結果を構造化データとして入力する：
- lint/型チェック結果
- テスト実行結果（pass/fail/coverage）
- セキュリティスキャン結果（gitleaks, semgrep等）
ツール結果なしの「感覚的ヨシ」を排除する。

### SAST先行注入の定量的効果（論文根拠: arxiv:2602.16741）

8モデル×9,000試行の実験で、SAST結果をレビュー前に注入することでベースライン失敗の47%が回復し、検出率96.9%に到達。商用モデル（Claude含む）は敵対的コメント注入に対して89〜96%の検出精度を維持するが、残り4〜11%の見逃しに対してセキュリティ系PRでは必ずSAST補完が必要。

- **必須化**: セキュリティ影響のあるPRでは、betterleaks/semgrep/trivy等のスキャン結果を玄人猫への入力に含めてからレビューを開始する
- **2段階検証**: SAST結果先行注入 → JiTTestsで境界値補完、の2段階パイプラインが最も効果的

## ブラインドレビュー原則（論文根拠: arxiv:2603.18740）

LLMレビュアーはPR説明文・コミットメッセージの「バグ修正です」「安全です」等のフレーミングに影響され、脆弱性検出率が最大93%低下する（確証バイアス）。自律エージェントモードでは攻撃成功率88%。

- **diff先行評価**: レビュアーはPR説明文・コミットメッセージを読む前に、コードdiffのみで仮評価を行い、仮評価を記録してから説明文と照合する
- **メタデータ除去**: セキュリティ関連のレビューでは、コミット者情報・PR説明を意図的に隠す「ブラインドレビューモード」を適用する
- **自律エージェントへの注意**: 仕事猫が玄人猫に指示を渡す際、実装者の主張（「テスト通過済み」等）をそのまま含めない。事実（テスト実行結果のログ）のみを渡す

## JiTTests — Just-in-Time使い捨てテスト（Meta研究由来）

PR差分から自動生成する使い捨てテスト。レビュー補助として活用する。

### いつ使うか
- 変更が3ファイル以上、かつ既存テストが変更箇所をカバーしていない場合
- レビュアー（玄人猫）が「テストカバレッジ不足」と判定した場合

### 手順
1. `git diff` から変更された関数・メソッドを特定
2. 変更箇所に対する境界値・異常系テストを生成（使い捨て前提）
3. テスト実行 → 失敗があれば実装にフィードバック
4. レビュー通過後、使い捨てテストは削除可（永続テストは別途作成）

### 注意
- 使い捨てテストはリポジトリにコミットしない（`tmp/jit-tests/` に出力）
- 永続テストの代替ではない。レビュー精度の補助ツール

## DB設計レビュー観点

DB変更を含む全タスクで、実装前にDB設計レビューを実施する。設計者≠レビュアー。

### レビューチェックリスト

| 観点 | 確認内容 |
|------|---------|
| **正規化** | 第3正規形以上か。非正規化がある場合、パフォーマンス理由が明記されているか |
| **インデックス** | WHERE/JOIN/ORDER BYで使われるカラムにインデックスが定義されているか。過剰インデックスはないか |
| **拡張性** | 将来のカラム追加・テーブル分割を想定した設計か。ENUMハードコードや固定カラム数に依存していないか |
| **命名規約** | snake_case統一。既存テーブル・カラムとの命名一貫性。略語の乱用がないか |
| **データ型** | 適切な型選択（VARCHAR長、INTEGER vs BIGINT、日時型等）。NULL許容の妥当性 |
| **制約** | PRIMARY KEY、FOREIGN KEY、UNIQUE、NOT NULL、DEFAULT値が適切か |
| **マイグレーション** | 既存データへの破壊的変更がないか。ロールバック可能か |

### フロー

```
DB設計書作成 → DBレビュー(edit:false) → [問題あり] → 修正 → 再レビュー → ... (最大3回)
                                         [問題なし] → API/UI設計フェーズへ
```

## API/UI設計レビュー観点

DBレビュー通過後に着手。API設計とUI設計は並行可。

| 観点 | 確認内容 |
|------|---------|
| **DB整合性** | APIのリクエスト/レスポンスがDBスキーマと一致しているか |
| **エンドポイント設計** | RESTful規約、命名の一貫性、適切なHTTPメソッド |
| **UI-APIマッピング** | 画面の表示・操作に必要なAPIが揃っているか |

## テスト品質ガイド（論文根拠: arxiv:2602.07900）

AIエージェントが生成するテストは「習慣の模倣」に陥りやすい。print文がassertの4〜5倍という実態が報告されている。
テスト量と問題解決率に統計的相関はない（83%のタスクでテスト有無は結果に無関係）。

- **assert重視**: テストには形式的な検証（assert文）を必ず含める。print文のみのテストは不可
- **量より質**: テスト数を増やすより、境界値・異常系の少数精鋭テストを設計
- **異常系テスト必須**: テスト計画には以下の異常系カテゴリを必ず含める。正常系のみのテスト計画は不完全として差し戻す
  - **無効入力**: null/undefined、空文字、型違い、範囲外の値
  - **境界値**: 最小値・最大値・ゼロ・負数・上限+1
  - **エラーハンドリング**: API失敗、ネットワークエラー、タイムアウト
  - **権限・認証**: 未認証、権限不足、トークン期限切れ（該当する場合）
  - **並行性**: 同時実行、競合状態（該当する場合）
- **テスト削減OK**: コスト最適化のためにテスト数を減らすことは許容（解決率への影響は-2%程度）。ただし異常系カテゴリを0にするのは不可
- **敵対的テスト推奨**: 可能なら変異テスト的アプローチ（意図的にバグを仕込んでテストが検出するか確認）

## 複雑コードへの構造的ヒント（論文根拠: arxiv:2512.14917）

LLMは以下のコード構造で理解精度が急落する。該当構造を扱う際はプロンプトに構造的ヒントを含める:

| 苦手構造 | 対策 |
|---------|------|
| 深いネスト（条件分岐/ループ） | ネスト構造の概要を先に説明 |
| クラス間依存（プロシージャ間コール） | 呼び出しチェーンの概要を付与 |
| 複合データ型（カスタムオブジェクト） | データ構造の型定義を明示 |
| サードパーティAPI呼び出し | APIの振る舞いを簡潔に説明 |
